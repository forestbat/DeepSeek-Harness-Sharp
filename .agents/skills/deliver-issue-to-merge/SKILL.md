# 从需求讨论交付到实际合并

遵守当前项目规则，以实际合并和交付回写为终点，不把代码完成、subagent 返回、推送成功或 CI 全绿当作全部完成。
沿用已有 Discussion、Issue、PR 和验证入口，不为套用流程而重复创建。
本技能不授予额外的公开写入、权限提升、破坏性操作或范围扩张授权。

## 1. 确认需求与执行契约

- 读取相关 Discussion、Issue 正文以及完整分页的维护者评论、审阅正文和行内意见，核对最新决定而非只看最后几条回复。
- 核实当前仓库、主线、分支、已有工作树所有权、相关 PR 的真实状态、当前 head 的 CI 和实际 GitHub 权限。
- 将功能目标、非目标、依赖、修改边界和可观察的验收标准固定到 Issue，已有 Issue 直接复用。
- 需要新建 Issue 时，在用户授权范围内提交并链接来源 Discussion，避免把未批准建议写成既定要求。
- 把用户举例推广到明确的规则和边界，不把一个示例当作全部情况。
- 只在无法从代码、文档或讨论确定且会实质影响产品取舍时询问，不以反复确认代替调查。
- 建立 TODO 和依赖关系，逐条保留用户要求，不擅自缩减验收范围。

## 2. 按 PR 隔离工作与所有权

- 默认每个 PR 使用独立分支和独立 worktree，不在主工作树交叉开发多个功能。
- 登记 Issue/PR、worktree、分支、准确基线、负责代理、文件边界和验证资源，优先沿用已明确归属本任务的工作树。
- 不接管他人的分支、未提交修改、端口、进程或验收目录。
- 仅将无前置依赖且接口与修改边界可分离的非琐碎任务并行，不为凑并行而启动空转代理。
- 并行交付时为每个 worktree 指定一个专属 subagent，不让多个代理无协调地编辑同一工作树。
- 由主 agent 负责拆分、接口契约、唯一集成负责人、跨 PR 依赖、验证调度及公开交付，不把顶层规划整体外包。
- 有依赖的任务按依赖顺序推进，提前准备依赖分支时明确实际基线与最终整合门禁，不假装依赖已经合并。
- 发现共同底层改动时先明确其归属与接口，不在多个 PR 各自复制一份实现。

给负责代理交接以下内容，并保留相关项目规则：

- 目标和非目标、Issue/PR 与讨论决定。
- 准确 worktree、分支、基线和不得触碰的资源。
- 允许修改的职责边界与共享接口契约。
- 每项验收标准及所需真实场景。
- 优先使用 Rider MCP 分析、修改、检查与 xdebug 调试的要求。
- 不在并行实现过程中各自启动构建、lint、测试或格式化，交回主 agent 集中调度验证的要求。
- 隐私、资源限制和回报已改文件、证据、未解决问题的要求。

## 3. 实现并取得真实证据

- 先读实际实现和调用关系，复用现有边界，不依据可能过时的注释判断行为。
- 优先使用 Rider MCP 与既有调试流程，工具不可用时如实记录后采用可用的编译器和运行手段，不冒称已完成 IDE 检查。
- 修复 bug 前取得失败证据，修改后验证同一消费者行为，测试不得复制业务逻辑或断言偶然的事件形态、文案和接线。
- 由主 agent 在改动收敛后集中调度构建、静态检查和受影响验证，失败再进入下一轮实现与验证。
- 将代码开发并行与重验证并行分开，worktree 只隔离文件，不隔离内存、CPU、端口、进程和凭据。
- 本项目重验证默认使用任务自有资源边界：4 GiB 内存、零 swap、单 worker，同一时刻只运行一个本地重验证任务。
- 在自有后台显示环境运行真实 GUI，不抢用户前台焦点或注入用户桌面的键鼠。
- 先通过所需组件/集成门禁，再运行真实主流程，不用 mock LLM 或 mock TUI 替代真实表面。
- 给所有调用真实 LLM 的测试标记 Category=LlmSmoke，快速测试过滤模型、GPU、渲染压测等对应类别。
- 将测试、真实 CLI/GUI/TUI 场景和资源释放的证据对应到准确源码版本，区分通过、失败、跳过、未运行和工具不可用。
- 改动后重跑受影响路径，不把旧 head、旧 CI 或历史模型调用冒充当前版本重新验证。
- 不通过扩大超时、增加无依据重试、隐藏异常或删除消费者断言掩盖失败。

## 4. 检查隐私并提交 PR

- 按范围更新用户文档，删除本次替换后确实废弃的代码和临时脚手架，不把开发进度写进 README。
- 推送前核对最新主线与实际依赖，必要时整合并验证，不强推或覆盖他人工作。
- 检查完整公开文件清单、实际提交差异以及 author/committer，使用公开 GitHub noreply 身份。
- 不公开真实用户名、home、hostname、私人端点、令牌、凭据、用户配置或会话数据。
- 将 plans、原始日志、截图、诊断快照和私有验收资料保留本地，逐个实际 worktree 检查忽略边界，不依赖父仓库的忽略规则。
- 复用项目的秘密扫描能力，调查匹配结果，不把扫描失败写成成功，也不为规避泛匹配删除有效示例。
- 创建独立 PR 并链接 Issue，说明实际实现、验收结果、跳过和已知限制，不写未经运行的通过结论。
- 对公开写入精确回读，结果含糊时先确认服务端是否已经落地，避免重复创建 Issue、PR 或评论。

## 5. 持续处理 CI 和维护者反馈

- 等待当前 PR head 的正式 CI，使用可等待的后台监视器，不忙轮询、不反复读取相同日志或启动重复本地验证。
- 新消息到来后完整读取普通评论、review 正文和行内意见，不能只看最近几条而漏掉旧的撤回或修改要求。
- 以原始失败步骤、断言、调用路径和运行现场区分实现缺陷、测试契约问题与基础设施故障，不凭 CI 红灯直接归因环境。
- 将修改要求交回该 PR 对应的负责代理和 worktree，在同一个 PR 更新，不混入其他任务。
- 需求有实质变化时先同步 Issue/Discussion，再实现，不把旧批准扩大为新功能授权。
- 修改后执行受影响验证、隐私检查、推送，再核对新 head 的正式 CI，重复此循环直到要求全部处理。
- 无新信息时等待并保留准确进度，不把等待阶段当作交付完成，也不重复发布相同进度评论。
- 实际遇到外部权限或维护者决策门禁时完成所有可达工作，明确阻断、已尝试操作和所需行动，保留任务未完成状态，不越权或盲目重试。

## 6. 核实 merge 并回写交付

- 在授权和权限允许时执行普通、指定受测 head 的合并，不使用管理员绕过、擅自提高权限或替维护者批准。
- 没有上游写入权限时请求有权限的维护者合并，不用 fork 的写入权限冒充上游权限。
- 直接核对 PR 的 merged 状态、真实合并提交和 Issue 状态，不把 mergeable、临时测试 merge SHA、CI 成功或分支消失当作已合并。
- 对比合并源码与最终受测源码，源码不同则调查差异并补受影响验证，完全相同则说明复用的是同一源码证据而非重新运行。
- 再次检查维护者反馈无待办，将实际交付、合并链接、验证出处和剩余路线图范围回写原 Issue 与 Discussion。
- 清理精确归属本任务的临时凭据、工具和进程，确认释放，不删除用户原始配置、无关会话或未提交工作。
- 不自动删除可能仍保存工作或验收资料的 worktree，删除前遵守项目所有权与破坏性操作规则。
- 只有全部验收有对应证据、维护者要求已处理、所需 CI 已成功、PR 已实际合并且交付回写完成，才标记任务完成并进入下一个独立功能。
